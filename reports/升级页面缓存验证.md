# 升级页面缓存验证

日期：2026-11-13。修复提交：`b822551`，已随 [v2.2.2](https://github.com/lance-donif/autoSkill/releases/tag/v2.2.2) 发布，三平台附件核对见[发布记录](发布记录-v2.2.2.md)。v2.2.1 已包含 Apple 风 UI，但不包含本次缓存修复；最终发行状态以 `release-status.json` 为准。

使用者已确认：浏览器直接访问 8787 看到新界面，DSH 内显示旧界面，清缓存后恢复。旧服务只对 API 返回 `no-store`，HTML、CSS 和 JS 使用固定地址；包内 UI 与源码一致，不能证明浏览器已经重新加载了这些字节。

## 修复及自动检查

- DSH 插件每次 `apply` 生成新的非秘密 activation，两个面板共用，普通 React 重渲染保持稳定。新激活绕开旧 HTML 的缓存键，不清理 Cookie 或任何用户存储。
- 服务端为整个 UI 文件树计算内容 SHA-256，页面资源统一使用 `/_ui/<hash>/...`；相对静态/动态 module import 沿用同一个版本路径。只修改深层文件也会更新整个入口命名空间。
- HTML、旧资源地址和版本化资源返回 `Cache-Control: no-store`；不复用仅根据文件时间及大小的旧 304 校验。原接口、页面路由与数据保留行为不变。

## 独立真实浏览器验收

另一 agent 使用真实 Chromium、同一 browser context、同一 UI origin、实际 `plugin/client.js` 的 `apply` 和产品 `create_app` / `mount_ui` 执行。页面为合成版本标记，宿主只提供最小 React/slots/ModuleLoader 接口。没有使用 Playwright route、禁用缓存或新建上下文绕过旧状态。

| 场景 | 实际结果 |
| --- | --- |
| 旧缓存预热 | HTML、CSS、入口模块、静态子模块、动态模块及深层子模块共 6 类资源再次加载时，服务端新增请求为 0；CDP `fromDiskCache` / `requestServedFromCache` 确认真实命中 |
| 负对照 | 换成新服务后，新外部标签页显示 V2，沿用旧 iframe URL 仍显示 V1 |
| 正常重新激活 | 同一上下文执行真实新版客户端 `apply`，新 activation 使 iframe 的 HTML、CSS 和所有模块完整更新为 V2 |
| 同元数据内容变化 | 只改深层 leaf 为 V3，保留大小、mtime 和其他文件；命名空间变化，浏览器实际加载 V3 |
| 条件请求 | HTML、旧 CSS/JS、深层 JS、版本化 JS、API 共 7 类请求携带旧 validators，全为 200 和 `no-store` |
| 用户状态 | 两次升级后合成 cookies、localStorage 均保留，没有 `Clear-Site-Data`，没有页面 JS 错误 |

首次两次验收准备受到旧测试 HTTP 服务的预连接干扰：关闭监听后旧已接受连接仍返回旧字节，CDP 明确不是缓存命中。修正该测试脚手架，使其完整关闭自身连接以模拟旧服务进程退出；没有修改产品或清除浏览器缓存。原尝试与最终通过证据分别保留，未将它们混写成一次全通过。

新版客户端必须先由 DSH 加载。已驻留的旧 ModuleLoader/iframe 不会因为磁盘文件更新而自行运行新代码，因此升级步骤仍需重启 DSH 或重新加载插件模块。此验收不是实际 DSH WebView 或 Windows/UOS 实机验收，也不宣称旧文档完全没有导航时会自行变化。操作说明见[升级与数据保留](../docs/升级与数据保留.md)。
