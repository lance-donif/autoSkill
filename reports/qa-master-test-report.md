## 问题清单

### QA-001：宽松响应 Schema 可绕过业务断言要求

优先级：P1。

复现：在有效 API 用例中设置 `assertions={"status":200,"schema":true}`，访问返回 HTTP 200 的本地模拟接口。

实际：validate 没有报错，run-api 判为 Pass。响应没有被验证为符合任何具体业务规则。空对象 Schema 同样需要进一步约束或显式标注为仅检查 JSON 可解析性。

预期：普通业务用例不能以布尔 true 作为业务/结构断言的替代。若有意只测可用性，应显式区分测试类型，并限制报告结论。

建议：增加断言有效性校验，要求可验证的业务字段或非空结构约束；保留明确的可用性用例例外。

### QA-002：导出器未自动拦截明文认证数据

优先级：P1。

复现：把纯合成的 Authorization 值写入测试用例 headers，再导出接口工作簿。

实际：合成认证字符串原样出现在 Excel 的 Headers 列。没有使用真实凭据，本次没有真实秘密泄露。

预期：规范虽要求只保存环境变量引用，但导出阶段仍应拒绝或脱敏敏感字段，不能完全依赖操作者遵守说明。

建议：保存与导出均检查认证字段；只允许受控环境变量引用或脱敏值，并覆盖嵌套请求数据与扩展字段。简单关键字过滤不能替代项目数据检查。

### QA-003：JSON 顶层类型错误造成程序异常

优先级：P2。

复现：将 api-cases.json 从用例数组改成 `{"cases":[有效用例]}`，再校验。

实际：validate 触发 AttributeError；CLI 的异常处理没有覆盖该异常类型。

预期：返回明确的“用例文件必须是数组”校验错误及非零退出码，不产生未处理异常。

建议：先校验项目文件与数组容器，再校验数组元素；同时检查元素、需求和结果文件的顶层类型。

### QA-004：内容变化但修订号未变化时，旧 Pass 仍然有效

优先级：P1，属于存储规范尚未自动落实。

复现：执行用例得到 Pass，修改 expected 字段但保持 revision 不变，再 validate 并构建导出模型。

实际：校验没有报错，当前导出模型仍显示原来的 Pass。

预期：规范要求内容修改递增 revision，但缺少保存入口与内容校验值时，系统无法自动发现违反规范的修改。

建议：提供统一的用例保存/更新命令，自动快照与递增 revision；结果同时保存执行时用例内容哈希，导出时验证哈希。用例内容哈希与运行结果文件哈希用途不同。

### QA-005：递增用例修订后，重新执行在归档之前被阻断

优先级：P2。

复现：先执行 revision=1，再把用例改成 revision=2，运行 run-api。

实际：run-api 首先对旧执行结果进行严格校验，返回“旧版本结果，先归档后再执行”；程序尚未运行到自身的归档步骤。当前命令集合没有独立归档命令。

预期：旧结果不得作为新版本的有效结果，但应提供可用的归档并重跑流程。

建议：拆分“定义校验”和“当前结果校验”；重跑先验证定义、归档旧结果，再执行并校验新结果。亦可提供显式 archive/reset-current 命令。

### QA-006：非法 JSON Pointer 转义未被拒绝

优先级：P2。

复现：设置 `json_equals={"/bad~2key":0}` 后校验。

实际：validate 没有报错；解析器只替换 ~0 与 ~1，其他转义被当成普通键处理。

预期：非法转义应在执行前明确报错，避免把断言配置错误混同为业务失败。

建议：校验每段 Pointer 转义仅允许 ~0 与 ~1，补充空 Pointer、数组索引和包含斜杠键名的回归样本。

- 真实网站与 OpenAPI 的端到端业务测试，以及有状态数据初始化与清理。
- DOCX/PDF/扫描件/Excel 需求输入的端到端解析及需求遗漏率。
- 外部 JSON Schema 引用、网络中断、超时和跨域重定向的完整异常矩阵。
- 并发编辑、自动版本迁移、第三方测试平台导入导出与 CSV 适配。
- 原生 Excel 打开或渲染后的视觉排版。
- 正式安装后的技能发现与调用；当前安装仍未成功。

## 建议处理顺序

1. 优先修复误判通过、认证字段导出、内容变更沿用旧结果三个 P1 问题。
2. 修复容器校验、版本重跑流程与 Pointer 校验三个 P2 问题。
3. 增加统一用例保存入口和针对上述问题的回归测试。
4. 修复后重新运行本轮测试，再用用户指定的授权测试网站执行 UI/API 联合验收。

本轮没有将测试问题视为已修复，也没有将本地模拟接口成功视为真实业务测试通过。
