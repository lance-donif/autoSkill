## 测试背景：ISTQB 软件测试七大原则

用户要求把以下原则放入上下文，用于后续需求分析、用例设计和结果判断：

1. **测试能发现缺陷，不能证明没有缺陷。** 全部用例通过，不代表系统没有其他问题。
2. **穷尽测试不现实。** 除极简单的情况外，应按业务重要性和风险选择测试重点。
3. **尽早测试节省时间和成本。** 需求阶段就审查和设计用例，不必等开发完成。
4. **缺陷往往集中。** 少数模块可能包含多数问题，实际容易出错的地方应重点检查。
5. **测试会逐渐失去发现新缺陷的能力。** 随需求和问题补充用例、调整数据；已有回归测试仍有价值。
6. **测试依赖上下文。** 根据项目、环境和实际使用方式选择合适的测试方法。
7. **没有发现缺陷，不等于满足用户需要。** 还要检查业务目标和真实使用需求是否得到满足。

这是测试原则，不是新增功能清单。执行中心的用例可以逐步完善，结论只覆盖实际测试的范围。

依据：ISTQB CTFL v4.0.1（2024-09-15）第 1.3 节，第 17—18 页；上面是中文简述。
官方原文：`https://istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf`

## 一、已经确认

### 1. 开发者提需求时，自动一起产出测试用例

autoSkill 主要给开发者使用。新项目、已有项目的新需求都适用，不要求先有测试网址。

例如，开发者说：

> 给订单系统增加退款功能：未发货可以退款，已发货不能退款。先分析需求，给我开发计划。

harness（开发者使用的 AI 开发工具）识别需求后，应一起给出：

- 需求分析。
- 开发计划。
- 测试用例 Excel，例如“未发货退款成功”“已发货退款被拒绝”。

开发者不用另外说“生成测试用例”；明确要求只生成用例，也支持。

用例表沿用 14 列格式，刚生成时是“未执行”。需要测试时，再选择环境执行，把结果填回原表。同一会话重复提交同版本需求，复用原任务和原表；需求不清楚时先问清楚，不编造预期。

**用户已确认：“ok，这个没问题，下一个。”**

### 2. 交付文件的规则（已确认）

下面这些是用户已经明确要求的：

- 只有一个需求：直接放在 `autoSkill交付/`，不建需求子文件夹。
- 后来新增需求：再用各自的子文件夹区分。
- 用例 Excel 只展示最新版，不另交付初版。
- 测试报告和 Bug 清单每次生成新文件，旧文件保留。
- 报告文件名带日期、小时、分钟，不带秒；同一次执行的两份报告用相同时间。同一分钟内再次执行时，自动加序号后缀（如 `测试报告-20261126-1430-2.md`），不覆盖旧报告。
- 截图、日志、临时文件等放在 autoSkill 数据目录，不散落在开发项目里。
- 同一需求补充规则时，更新原用例表；新增或修改过的用例需要重新验证，旧报告保持原内容。
- 第二项独立需求出现时，把原需求的用例和历次报告一起归入对应子文件夹。如果 Windows 上目标 Excel 正被打开导致无法移动，不静默失败，直接提示用户先关闭正在打开的 `功能测试用例.xlsx` 后再继续。
- 内部按项目、需求、每次执行区分证据，并保留旧用例内容，用于查明以前测了什么。用户交付目录仍只展示最新用例；优先复用现有内部存储。
- 用户手动修改过 Excel 时，先保留人工内容，说明差异并展示合并后的例子，用户确认后再更新。
- 请求确认时，使用当前对话的风格：讲清具体改了哪里、用户会看到什么，再问是否这样更新；不要只显示技术名词或笼统的“存在冲突，是否覆盖”。

只有一个需求、执行两次后的示例：

```text
autoSkill交付/
  功能测试用例.xlsx
  测试报告-20261126-1430.md
  Bug清单-20261126-1430.md
  测试报告-20261126-1700.md
  Bug清单-20261126-1700.md
```

以后有多个需求时，按这个方向整理：

```text
autoSkill交付/
  退款需求/       ← 这项需求的最新用例和历次报告
  优惠券需求/     ← 另一项需求的用例和报告
```

尚未执行的需求只有用例表。以上是期望的文件样子，不表示程序已经实现。

用户已确认全部 7 个场景，并要求人工修改时的确认文案也沿用当前对话风格，随后回复：“没问题了，下一个。”

## 二、第三项与第四项（均已确认）

### 第三项：Linux 同步、平台登录与错误文件（已确认）

**已明确：开发电脑和 Linux 部署的是同一个 autoSkill，两端都有相同的导入、导出能力。** Linux 也能导出用例，开发电脑也能导入；两端都能导出本机执行产生的错误资料。下面的传递方向只是使用示例，不是功能限制。

**Linux 的定位已明确：没有模型的用例执行中心。** 多位开发者会把用例放进来，中心依靠已经提供的用例和配置执行。需求分析、设计新步骤、分析并修复用例由开发侧 harness 完成，不能假设 Linux 上有 AI 自动补齐。多人提交、任务排队和账号相互影响属于需要考虑的日常情况。

**用例是逐步完善的。** 开发可以逐批增加用例、根据实际运行修正用例和配置，不要求所有项目、所有用例一次准备完整。用户已确认自动处理所提供资料的方向，接下来讨论用例进入中心后的执行和更新。

**环境配置也需要随用例传递。** 本机可能免登录，执行中心可能需要账号登录，也可能使用不同登录方式。具体如何携带登录步骤、账号和变量，以及已有环境如何更新，接下来用例子确认。

**传递方式已确认，用户补充了原因：开发环境与测试环境隔离，只能通过 FTP 交换数据。** 用例、环境、登录资料和错误包都通过 FTP 跨环境传递。导出／导入是两端本地的文件操作，导出的包仍需经 FTP 送到另一端，不是新增直连通道。

- **送入用例：**开发通过 FTP 上传到 Linux 指定目录，或者使用导出、导入。autoSkill 要明确告诉开发应该传哪些用例文件。
- **取回错误：**开发也通过 FTP 或导出方式，收集 Linux 上执行失败的用例和报错信息，带回开发侧排查。

已经确认的传递方式：

| 方式 | 送入用例 | 取回错误 |
| --- | --- | --- |
| 指定目录自动接收 | 把整理好的用例包通过 FTP 放入接收目录，另一端自动导入 | 从配置的错误输出目录通过 FTP 取回对应执行的错误资料 |
| 手动导出／导入 | 任一端选择用例并导出，包经 FTP 传递后，在另一端网页手动导入 | 任一端都能导出失败用例和错误资料，由用户自行传递给 harness 分析 |

错误资料包含失败时实际执行的用例、报错说明、已有截图和相关请求响应／日志，由用户导出后交给 harness。完整约定见下方“错误资料导出”，不增加错误记录导入功能。

两端都可以配置接收目录和错误输出目录。同步冲突保留本地、Linux 服务显式配置无头已经确认，不重问。暂不增加 autoSkill 自带 FTP 客户端的开发范围。

此前的“运行环境稍后配置”已被用户纠正：环境需要一起同步；“首次接收时增加尚未在本机执行的描述”已被否定，不增加这段界面文案。执行记录仍保留真实来源，不能把别处的执行冒充为本机执行。

**执行中心的日常处理规则（已确认）：**

- **同步范围维持现有规则**：只同步通过状态的用例（按个人 skill 定位，不放开未通过用例同步）。
- **跨环境包形态统一为“单 zip 进、单 zip 出”**：导出/待传用例包统一生成 1 个可直接 FTP 上传的 `.zip`（自动包含所选业务用例、依赖前置、环境地址、变量和登录配置）并直接提示文件路径；错误输出目录与网页手动导出均输出 1 个 `.zip` 错误包（含失败用例、环境、账号、失败详情、截图和日志），方便 FTP 一次拖走交给 harness。
- **中心环境/账号保护与冲突分离**：多人提交不同用例时合并到对应项目；重复传入相同包不重复新增。中心已存在同名环境或账号时，导入默认保留中心本地的环境地址和账号（仅在中心尚未配置，或在冲突处理中显式选用传入时才更新）；冲突界面将“业务用例”与“环境/账号”分开勾选，允许“用例用传入、环境/账号保留本地”。
- **多人 FTP 同步防护**：导出包文件名默认带时间（到分钟）加简短后缀避免撞名覆盖；后台扫描遇到尚未传完的半截包先延后到文件稳定后再导入，不立刻误报失败；用例内部使用唯一标识（与界面显示的业务编号分开），避免多人各自新增时误判冲突。
- **执行时机与定时任务**：上传只接收和更新，不触发执行；由手动点击“运行”或定时任务触发。定时任务新建/编辑时单独保存其使用的“环境”和“账号”（默认带出项目默认项），在“测试用例”页临时切换不影响已设好的定时任务。
- **执行隔离与异常留证**：使用同一平台、环境和账号的执行依次排队，避免共享登录和测试数据互相影响；已经开始的运行使用启动时的用例、环境和账号配置，新上传内容用于后续运行。账号失效、缺少变量、找不到项目入口或遇到需要人工确认的登录时，给出具体失败原因和现有证据，不靠模型补操作、不无限等待。退款、下单等步骤超时或中断时保留现场证据，不盲目自动重做。
- **旧用例维护**：同步包中未包含的用例保持保留，不隐式删除；彻底废弃的旧业务用例由用户在页面中手动删除或停用。通过错误包修复 Bug 后，若原用例未覆盖触发条件，harness 顺带询问是否补充回归用例，确认后再加。

### 登录准备：自动处理用户提供的资料（方向已确认）

- 用户希望第一期先能用，重点处理账号密码登录；其他登录方式以后按实际需要补充。
- 用户可以提供登录代码、接口文档，也可能提供 Postman 脚本。只读取已经提供或明确指定的资料，**不自行扫描项目寻找资料**。
- 用户提供的信息足够时，harness 自动整理登录步骤、环境和相关配置，随用例一起打包，不要求用户学习专门话术或手写脚本、JSON。
- 只差账号等信息时，明确指出缺什么，让用户决定是否补充。选择先跳过，就继续不依赖这项信息的工作；不把登录当作已经准备完成。
- 用户后来补齐资料后，继续完成原任务，不让用户从头配置。
- 开发与测试隔离，测试侧的登录要到执行中心实际验证；不能把资料整理完成说成已经在测试环境登录成功。
- **已明确：不新增面向用户的“验证登录”功能或按钮。** 用户运行用例时，执行器按环境配置完成登录并检查是否成功；无需登录的环境直接执行业务步骤。需要登录却失败时，停止依赖该登录的业务步骤，在现有执行结果里记录原因。

例子：用户已经给了测试地址、登录请求和账号，harness 就把配套登录处理好；如果没给账号，则问：“登录方式已经有了，还缺测试账号。现在补充，还是先跳过登录准备？”

### 冲突处理：入口已确认，沿用现有界面风格

- 入口为“数据管理 → 同步记录”，有冲突的条目提供“处理”按钮，左右对照“当前版本”和“传入版本”。
- 操作是“保留当前”“使用传入”“导出两版”。FTP 自动接收和手动导入共用这个入口，未处理时保留现有内容。
- 两边修改都需要时，导出两版，经 FTP 交给开发侧 harness 合并。具体改动让用户看懂并确认后再传回；Linux 不靠模型合并。
- 用户已接受这个入口，要求界面风格一致、不要漏内容。沿用现有面板、按钮、表格和主题，不加多余说明；对照与导出要完整包含受影响的用例、前置、断言、环境和登录配置。

以上为确认的产品方向，尚未修改功能代码。用户回复：“没问题了，下一步。”

### 上传与执行时机（已确认）

- 用户已确认：第一期上传只接收和更新用例，上传本身不触发执行；用户点击“运行”，或由已有定时任务按时间和范围执行。
- 用例可以逐批补充；第一次只有 2 条退款用例，就先接收这 2 条，剩余场景以后补充。
- 登录及成功检查作为运行时的内部步骤，不提供单独的“验证登录”操作。

### 用例更新（已确认）

- 后来再补 3 条新用例，加到原项目，已有用例保留；重复上传同一包不重复新增。
- 修订原有用例时更新对应条目，遇到本地修改按已确认的冲突方式处理。以前的运行结果仍对应当时的版本。
- 只上传其中 1 条修订用例时，不删除包里没有包含的其他用例；没有上传不代表要求删除。
- 缺账号或登录失败时记录具体原因，其他不依赖这项登录的用例继续；以后补齐配置再执行。
- 正在进行的运行保持启动时的用例和环境，更新用于后续运行，不改变正在执行的内容。

用户已确认：“新增就补充，修改就更新，没上传的保留。”重复上传不重复新增，旧执行记录对应当时版本。

### 任务排队与平台登录

**基础排队方式已确认：**同项目任务依次执行，全局默认最多同时运行 2 个任务，其余排队；手动和定时任务共用队列。用户随后要求：订单和库存使用同一套登录时，应复用登录态。

**新增业务情况：**用户有平台，平台根据登录账号显示不同项目入口。此前“项目不同就可以同时执行”的例子，要结合共享账号和切换项目是否互相影响调整。

**入口形式已确认，两种都有：**在 A 网址登录后跳转到 B 网址；或先进入平台首页，再从导航进入项目子网址。不能只按登录页的网址判断业务项目。

登录缓存方式已确认：

- 将平台登录与进入项目分开。例如账号 A 在业务平台能进入订单和库存，账号 B 只能进入库存。
- 只有同一平台、同一环境、同一账号，且属于同一套登录的任务，才复用有效登录态；不根据账号密码恰好相同就跨平台共用。登录失效后按已有流程重新登录。
- 账号 A、账号 B 各保存自己的登录状态，切换使用时不覆盖另一份；两个账号都能进入库存项目时，仍按任务指定的账号执行，不随意选一个缓存。用户已确认这个复用方式。
- 两种入口都保留实际登录与跳转流程。跨网址时按各网址恢复登录产生的状态，需要时正常经过平台跳转；从导航进入项目时，复用登录后仍进入并核对指定项目。缓存不代替项目选择，也不保证永久有效。
- 每条业务用例明确目标项目入口。执行时自动完成平台登录、进入目标项目并核对，再执行业务步骤；换项目时复用平台登录，仍重新进入并核对目标项目。
- 平台、账号、环境和项目入口关系从用户提供或明确指定的资料整理，随包传递；Linux 按确定步骤执行，不扫描项目、不依赖模型寻找入口。

**共享账号排队已确认：**同一平台、环境和账号的订单、库存任务依次执行；不同账号运行不同项目时可并行，同项目仍依次执行，全局默认最多同时运行 2 个任务。排队由程序内部处理，不增加用户操作。

**找不到项目入口已确认：**需要进入目标项目却看不到入口时（例如账号登录成功但平台导航中未找到“订单”入口），在执行记录中写明具体原因并附上当时截图，停止依赖该入口的后续步骤。

目前代码按站点识别项目、按项目保存登录态，尚未实现上面的平台级、多账号缓存。这些都是程序内部处理，不新增登录缓存按钮或平台管理页面。

### 错误资料导出（使用方式已确认）

**已明确：软件支持导出失败用例和报错资料，用户自行决定怎样传给 harness。** 不需要导入本机 autoSkill，也不新增导入错误记录的功能。普通用例包继续支持已确认的导入／导出。

例如订单项目运行 5 条用例，其中 1 条退款失败。在配置的错误目录按本次运行直接输出 1 个 `.zip` 错误包，网页“执行记录”导出的也是同一份 `.zip` 包，方便 FTP 一次拖走。

- 包含失败时实际执行的用例及必要前置、当时的环境配置与使用账号、失败步骤、期望与实际结果，以及已有截图、请求响应和相关日志。
- 记录对应项目、运行编号和执行时间，文件名时间仍只到分钟。引用的证据一并打包，用包内路径关联，开发拿回后能查看。
- 用户导出或从错误目录取回资料后，自行交给 harness 分析，autoSkill 不负责把文件发送给 harness。开发与测试跨环境传文件仍使用 FTP。修改方案先让用户确认，再修订用例或代码；修复后的用例传回中心重测，旧失败记录保留。

用户已确认继续下一项。错误资料包含上面展示的用例、环境、失败详情和已有证据；由用户交给 harness，不增加错误记录导入。功能尚未实现，一次运行的错误包对应当时的实际版本。

### 第四项：页面里查看和使用环境、账号与变量规则（已确认）

用户要求：用例、登录信息和环境变量要在页面上容易理解、容易操作，且从平台角度统一抽象（不把“本机”特例化成免登录）。以下方案已确认：

- **平时运行（测试用例页）：**沿用“测试用例”页，在每个项目标题旁放环境和账号选择，下方保留用例表。多项目时各自显示所选环境和账号，顶部范围栏不再重复放环境选择。
- **按环境配置统一决定是否显示账号：**所有环境平等，只要当前所选环境配置为“需要登录”，项目标题旁就显示账号下拉框（缺少账号时在对应位置提示“未配置账号”）；配置为“无需登录”时，不显示账号下拉框。导入包里配好的默认环境和账号自动带入；切换环境时一起切换地址、变量和对应账号选项。
- **用例级账号覆盖：**项目标题旁选的账号作为本次运行的默认账号；如果某条用例明确设定了“不登录”或指定了特定账号（例如未登录拦截、权限对比用例），执行时按用例自身设定跑，执行记录写明实际使用的账号。
- **修改配置（项目设置侧栏，适配几十个 key）：**
  - 留在原有“项目设置”侧栏中（适当加宽便于编辑表格），顶部先切换环境，一次只看 1 个环境；新建环境时支持复制已有环境的变量名。
  - 内部拆成两个标签页：**「基础与登录」**（项目地址、项目入口、登录方式、账号密码、执行超时）和 **「变量 (数量)」**（专门承载几十个 key）。
  - 变量页支持：① 搜索变量名或值 + **只看空值**筛选；② 紧凑表格行内直接编辑（表头固定、表格内部滚动）；③ **表格 / 批量文本**（`KEY=VALUE`）一键切换，方便成批粘贴与对照。
  - 共用同一平台账号的订单、库存项目引用同一份账号信息，账号旁标明平台和环境归属；修改一次，引用它的项目同步生效。点击保存只保存配置，不自动启动执行。
- **查看结果（执行记录）：**沿用“执行记录”，显示本次实际使用的项目、环境、账号和结果；历史记录不随当前选择改变，密码只在设置里明文显示。报告和记录并列写清「总用例 / 本次执行 / 通过 / 失败 / 受阻 / 未执行」及环境、账号，存在失败或受阻时不标为“全部通过”。
- **界面风格保持克制：**沿用现有表格、按钮、侧栏和明暗主题风格；不增加介绍段落、验证登录按钮或新的管理页面。

**同名变量的取值顺序（已确认）：**

- 按从高到低覆盖：**本次运行明确传入的值 ＞ 前置步骤实时取到的值 ＞ 当前环境的变量值**。
- `${ENV:NAME}` 专门读取本地凭据库或系统环境变量，不与 `{{变量}}` 混用。
- **运行前缺失变量检查：**点击运行或定时任务启动前，自动扫描本次选中用例用到的 `{{变量名}}`（排除前置步骤会提取的），如果当前环境和传参均无值，直接提前提示缺失哪几个变量名，不把未替换的 `{{...}}` 原样发给被测系统。

## 四、最后一轮复核：ISTQB 软件测试七大原则检查结论（已确认）

已对照 ISTQB 软件测试七大原则逐项复核，补齐的规则与口径已合入上文对应章节：

1. **测试能发现缺陷，不能证明没有缺陷**：报告与执行记录固定并列展示「总用例 / 本次执行 / 通过 / 失败 / 受阻 / 未执行」及环境、账号，结论只覆盖实际执行范围；有失败或受阻时不标为“全部通过”。
2. **穷尽测试不现实**：自动生成用例时按业务风险在现有优先级列标清高中低（核心主流程和关键校验排高优），便于先勾重点跑或配置定时任务。
3. **尽早测试节省时间和成本**：需求阶段产出用例、模糊点先问清；开发过程中规则或文案变化时，同步更新原用例表并标出需重验条目，不修改预期迎合代码报错。
4. **缺陷往往集中**：运行前检查本次选中用例用到的 `{{变量名}}` 是否在环境/传参/前置提取中有着落，缺项提前提示，防止几十个 key 漏填引发批量假失败。
5. **测试会逐渐失去发现新缺陷的能力**：同步包不隐式删除未上传用例，彻底废弃的旧用例由用户在页面手动删/停用；通过错误包修完 Bug 后，若原用例未覆盖触发条件，harness 顺带询问是否补充回归用例，确认后再加。
6. **测试依赖上下文**：所有环境平等按配置决定是否登录；项目标题旁账号作为默认账号，明确声明“不登录”或指定特定账号的用例按自身设定执行并如实记录。
7. **没有发现缺陷，不等于满足用户需要**：跨环境交接统一为“单 zip 进、单 zip 出”，减少开发手动拼文件的成本；页面对几十个 key 提供搜索、只看空值和批量文本切换。

> 注：以上复核仅覆盖本次目标与已知日常场景，不承诺已找出未来所有可能问题。
