# 升级与数据保留

升级保留项目、知识、用例、原生资产、工作流、凭据、保存的登录态、定时任务、运行记录和证据。不要把新包直接覆盖到旧目录，也不要删除旧工作区后重新导入项目包。项目分享包和升级备份用途不同；完整分享包仍不包含全部运行历史。

以下自动升级命令适用于 **v2.2.1 起包含 `autoskill-upgrade.py` 和 `package-manifest.json` 的新版离线包**；v2.2.0 不包含这两个文件。旧安装本身不需要认识 `upgrade` 命令：可以直接借用新包里的 Python 和独立升级器。Git 源码安装使用本文末尾的源码流程。

Linux x64 合成安装已通过 23 项专项，以及公共 CLI 升级后的 21 项、回滚后的 24 项数据保留检查。实际覆盖和平台边界见[升级保留数据验证](../reports/升级保留数据验证.md)。

## 升级会保留什么

`plan` 会列出实际目标、旧/新版本、数据目录、配置路径和发现的后台进程。数据路径包括旧安装默认 `autoskill/workspace`、当前 `AUTOSKILL_WORKSPACE`、显式 `--workspace`，以及默认/环境指定的 `autoskill-cases` 和已保存任务、运行记录引用的绝对用例表路径。命名会话的用例表位于工作区内，一并备份。

宿主配置中未传给当前进程的外置路径无法凭空推断。AI 应先读取现有 DSH 配置和启动环境，把实际外置工作区、其他用例表目录用重复的 `--workspace` 参数补全；自定义配置文件用重复的 `--config` 指定。`cordis.patch.yml` 和已有平台 `runtime-settings.json` 自动保留。外置目录不会被搬入安装目录，也不会在失败回滚时用旧备份覆盖。

备份覆盖完整数据树，包括 `.local`。仅对确切的 `.local/autoskill.db` 使用 SQLite 备份接口，合入已提交 WAL，保留文件权限；原生 SQLite 附件、不可变对象及冻结输入保持原始字节。工作区内链接的内容进入备份，并记录链接目标；恢复安装时保留链接关系。空目录也保留。机器锁文件 `.local/queue-worker.lock`、`.local/locks/*.lock` 和用例表目录的 `.autoskill-plan.lock` 不重放，排除项写入备份清单；完整旧安装仍单独保留。

备份目录含明文凭据和登录态。命令只返回路径、数量和检查结论，不回显凭据值。

## 让 AI 完成升级

向宿主 AI 提供新 Release ZIP 和旧安装路径，要求它依次执行以下操作即可，不需要额外的人工审批阶段：

1. 确认操作的是离线安装，读取旧配置，执行 `upgrade plan`，补全外置数据及配置路径。
2. 暂停这份安装的新写入；结束正在录制或执行的测试。升级器不会为了换包自动取消业务回放、录制或终止用户浏览器。
3. 执行 `upgrade prepare`，使用明确的安装外 `--job-dir`。需要自动停本安装的仪表盘和独立调度进程时加 `--stop-services`。
4. 保存返回的 `journal`。异步返回 `state=launched` 仅说明独立进程已经启动；轮询 `upgrade status JOURNAL`，直到 `prepared` 才继续。
5. 执行 `upgrade apply JOURNAL --stop-services`，保存交接收据，轮询到 `completed`。如失败，读取 `error`、`last_action` 和 `handoff.log`，使用同一记录 `recover`，不要重复创建并行升级。
6. 重启 DSH，或重新加载并启用原路径的 autoSkill 插件；独立使用时重新启动仪表盘。运行 `autoskill doctor --launch`，再核对原项目、凭据名、登录项目、定时任务与历史记录。

新版 CLI 的 `apply`、`rollback`、`recover` 会交给独立进程，待发起的短 CLI 退出后运行。它使用持久准备目录中的 Python 和升级器，桥接附件临时目录删除后仍可执行。HTTP 也通过短 CLI 交接，不会等待长驻仪表盘退出才永远无法开始。

`prepare --stop-services` 先复制并验证新包，再返回持久恢复记录，由独立进程停服务和备份。调用经由将被停止的仪表盘时，网络连接仍可能中断；使用事先指定的 `--job-dir/journal.json` 在安装外查询状态即可，不能把断连当成功，也不要盲目再创建一次任务。

### 升级后的页面与缓存

v2.2.2 起，插件每次激活会使用新的 iframe 页面地址；服务端为整套 CSS/JS 及其相对模块依赖生成内容版本路径，HTML 与静态资源均返回 `Cache-Control: no-store`。即使 ZIP 保留了文件时间、文件大小未变，内容变化仍会切换资源地址，旧条件请求也不会把新文件误判成 304。

升级后应重启 DSH，或完成插件模块的重新加载再启用。仅替换磁盘文件、保留已经加载的旧插件和旧 iframe，不会让旧执行上下文自动运行新代码。正常重新加载流程无需手动清浏览器缓存；实现不清除 Cookie、localStorage、登录态或用户偏好，也不会因普通面板重渲染反复刷新 iframe。证据与真实 DSH 验收边界见[升级页面缓存验证](../reports/升级页面缓存验证.md)。

## 手动升级：Linux / UOS

先下载正确 CPU 架构的 ZIP，解压到一个**新的临时目录**。以下路径仅为示例，实际使用时替换。准备来源使用原始 ZIP；新解压目录只提供 Python 和升级器。`-B` 防止 Python 在新包内生成不属于完整性清单的缓存。

```bash
NEW=/home/me/downloads/autoskill-new
PY="$NEW/autoskill/vendor/linux-x64/python/bin/python3"
HELPER="$NEW/autoskill-upgrade.py"

"$PY" -B "$HELPER" plan /home/me/downloads/autoskill-release.zip --target /home/me/apps/autoskill
"$PY" -B "$HELPER" prepare /home/me/downloads/autoskill-release.zip --target /home/me/apps/autoskill --job-dir /home/me/backups/autoskill-upgrade --stop-services
"$PY" -B "$HELPER" status /home/me/backups/autoskill-upgrade/journal.json
```

ARM64 包把 `linux-x64` 换成 `linux-arm64`。有外置工作区时，在 `plan` 和 `prepare` 同时加例如 `--workspace /home/me/autoskill-data --workspace /home/me/case-plans --config /home/me/custom.yml`。

等 `state=prepared` 后执行：

```bash
"$PY" -B "$HELPER" apply /home/me/backups/autoskill-upgrade/journal.json --stop-services
"$PY" -B "$HELPER" status /home/me/backups/autoskill-upgrade/journal.json
```

这里的独立 helper 已在旧安装外运行，`apply` 会直接执行并返回最终状态。若是新版 `autoskill upgrade apply`，则返回异步交接收据，需要继续轮询。重新启用插件或启动新仪表盘后，运行新安装的 `autoskill doctor --launch`。

## 手动升级：Windows

解压新的 Windows ZIP 到旧安装之外；在 PowerShell 中调用新包的 Python。例如：

```powershell
$NewPackage = 'C:\Downloads\autoskill-new'
$Python = "$NewPackage\autoskill\vendor\windows-x64\python\python.exe"
$Helper = "$NewPackage\autoskill-upgrade.py"

& $Python -B $Helper plan 'C:\Downloads\autoskill-release.zip' --target 'C:\Tools\autoskill'
& $Python -B $Helper prepare 'C:\Downloads\autoskill-release.zip' --target 'C:\Tools\autoskill' --job-dir 'C:\Backups\autoskill-upgrade' --stop-services
& $Python -B $Helper status 'C:\Backups\autoskill-upgrade\journal.json'
# Continue only after status reports prepared.
& $Python -B $Helper apply 'C:\Backups\autoskill-upgrade\journal.json' --stop-services
```

外置工作区、用例表和配置同样使用 `--workspace`、`--config`。如果 DSH、编辑器、终端当前目录或其他程序占用旧安装，Windows 可能拒绝重命名；升级器不会强制覆盖被占用的文件。退出占用这份安装的进程后，用同一 `journal` 执行 `recover`，再按状态继续。不要手动删除旧目录来“解锁”。当前自动测试在 Linux 上执行；Windows 和 UOS 尚需真实设备验收，不能把这些命令示例当作已完成实机测试。

## 失败、回滚与恢复

```text
autoskill upgrade status JOURNAL
autoskill upgrade recover JOURNAL --stop-services
autoskill upgrade rollback JOURNAL --stop-services
```

旧版本没有这些命令时，用新包外置 Python 执行 `autoskill-upgrade.py status/recover/rollback JOURNAL`。`recover` 读取持久阶段，处理未完成的准备、目录切换或回滚；重复查询、已完成后的重复 apply、已回滚后的重复 rollback 不会再次搬动数据。若要在已回滚后重新升级，准备一个新的任务目录。

新包先在目标同级目录暂存，核对完整文件集合和 SHA-256 后再切换目录。切换后运行 `verify` 和静态 `doctor`；对工作区备份副本运行新版数据库初始化、完整性和原表行数检查，实际数据不会在验证阶段被迁移。校验失败时恢复旧目录，保留失败的新目录和所有备份。成功之后请求回滚，会再次备份当前数据，把新增内容及删除状态带回旧程序；不会复活已删除的工作区或配置。回滚恢复会识别仍在运行的新目录，重新读取中断后产生的数据。

旧程序能否理解后来人工写入的新版本业务格式并非目录回滚可以保证；所有版本的原始副本和备份均保留供恢复。升级器不自动删除恢复目录、旧安装或失败暂存目录。

本地文件会刷盘，阶段记录原子替换，平台支持时在目录切换后刷新父目录。测试覆盖进程中断和模拟切换失败；未做物理断电、存储硬件故障或 Windows 文件系统故障注入。`completed` 表示安装完整性、静态运行依赖和数据副本迁移检查通过，**不表示浏览器已启动、业务用例已通过**；浏览器验收须实际执行 `doctor --launch`。

升级期间保持停写。升级器识别并可停止归属明确的 autoSkill 仪表盘、独立队列进程；录制/CDP、agent-browser 会话、运行中的原生子进程及回放会阻止切换。新版公共数据入口使用工作区共享维护锁，升级独占同一把锁；正常多会话操作仍可并发，升级期间的新写入明确失败后重试。它还持有已知写锁、检查备份前后及切换边界的数据变化。旧版本或外部脚本若绕开锁同时写文件，不能视为获得了全局文件系统事务；应停止这些写入方后重试。

## Git 源码安装

有 `.git` 的源码目录不会被离线升级器整体替换，以免移动仓库或开发改动。已有 DSH 插件若指向源码目录，继续更新同一目录即可：

1. 停用这份 autoSkill 插件/仪表盘，结束录制与回放，并停止属于该工作区的独立 `python -m autoskill.server.jobs` 进程。不要删除定时任务来停调度。核对 `.local/queue-worker.json` 的 PID、进程命令和工作目录后再终止该进程，避免 PID 复用误伤其他应用。
2. 在所有写入停止后，将整个源码安装复制到安装外备份目录；将实际外置工作区、外置用例表和配置另行完整复制。必须包含 `.local`，SQLite 主库、`-wal`、`-shm` 一起保留，不能只复制项目目录或单独拿主库。Linux 可使用 `cp -a`，Windows 可用资源管理器完整复制，并核对原始目录与备份的文件数量和哈希。复制期间重新出现写入时，停止写入后重做备份。
3. 执行 `git status --short`、`git fetch origin`、`git pull --ff-only`。有本地开发改动或分叉时，先在保留改动的分支上处理；不要使用 `reset --hard`、清理未跟踪数据或覆盖整个仓库。
4. 按源码安装方式更新依赖，再重新启用原路径的插件，运行 `autoskill doctor --launch`，核对数据和任务。

若要从源码改用离线包，把新离线包安装到另一个目录，并让它沿用已备份的实际外置工作区；不要把 Release ZIP 覆盖到 Git 仓库。旧源码与旧运行环境保留到新安装实际验收完成。
