# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

autoSkill is a local test system operated through an agent skill, CLI and dashboard. A host AI turns sources into requirements, scenarios and executable cases through a durable workflow; the kernel validates references, runs frozen inputs, preserves evidence and publishes validated changes. Browser recording and Playwright/Selenium/HTTP replay remain available directly. Native adapters preserve existing Python, Postman/Apifox and JMeter projects; the AI evaluation engine handles multi-turn HTTP/SSE/WebSocket conversations and asks the host for independent semantic judgements. It ships as an offline package and as a DeepSeek Harness (DSH) plugin. Model configuration belongs to the host, not a second SDK inside the kernel.

User-facing text (CLI messages, dashboard, SKILL.md, docs) is Chinese; code comments and docstrings are English.

## Static checks

`.github/workflows/lint.yml` uses `scripts/validate_review.py` for Ruff, Biome, conventions, review-tool regressions and selected workflow, knowledge and host contracts on every push and pull request. New code must pass them. The Python dispatcher calls the existing tools with argument lists and `shell=False`; it does not install or replace linters. CI provisions the pinned tools first. Local runs use installed binaries, keep logs and original exit codes under an explicit output directory (which may be outside the checkout), and isolate runtime data. See [Python review and validation](docs/Python代码审查与验证.md) for scopes and failure semantics.

- Do not weaken `ruff.toml` or `biome.json`, and do not add blanket suppressions. When a rule is wrong for one line, suppress that line with the rule name and a reason (`# noqa: T201  # the command's JSON output`, `// biome-ignore lint/<group>/<rule>: <reason>`).
- Neither tool formats this code base; do not run `ruff format` or `biome format` over existing files.
- `tests/test_conventions.py` holds the rules a general linter cannot see: colours only in `ui/css/tokens.css`, every `var(--token)` defined there, every IR action and assertion named and handled by both script generators, every CLI command documented in `SKILL.md` or `references/commands.md`, English code comments, LF and no tabs.

## Layout

- `skills/autoskill/` is the product. `SKILL.md` is the contract the agent reads, `app/autoskill/` the Python package, `app/ui/` the dashboard (plain ES modules, no build step), `models/captcha/` the bundled captcha model. `vendor/` (bundled runtime) is git-ignored. User data defaults to the external `~/autoSkill-data` directory (Windows `%USERPROFILE%/autoSkill-data`); explicit `AUTOSKILL_WORKSPACE` selects another root.
- `plugin/` is the DSH host: `index.mjs` starts the dashboard and registers skills with its confirmed data root; `host-adapter.mjs` delivers durable work to host sessions. Native tools, pre-step summaries and authenticated routes adapt the same kernel. The sole argument-free `/autoskill-use` command injects the registered skill into the current session without starting a model turn. `client.js` supplies collapsed inline tool results and sidebar dashboard panels; their actual origin comes from the host metadata route. Do not add an input dock, automatic task popups or forced host todo entries.
- In the offline package the skill sits at `autoskill/`, in a checkout at `skills/autoskill/`; `findSkillDir` in the plugin and `paths.SKILL` handle both.
- `scripts/` are maintainer build and release scripts; `reports/` holds review and validation evidence. Keep raw authentication and network captures out of public reports.

## Architecture

**CLI and services.** `cli.py` parses and dispatches; every command prints one JSON object. Exit codes: 0 ok, 1 a case failed, 2 the command did not succeed or the run was blocked. CLI and HTTP call the same application services. When the process is sandboxed (`paths.restricted()`), `bridge.py` forwards structured arguments and explicitly selected attachments to `/api/bridge`. Resolve file paths at the caller; preserve attachment content identity across temporary transport paths. Runtime context carries workspace, host session, browser session and workflow binding separately. Paginated service responses expose their cursor/snapshot contract; do not reconstruct full definitions from display summaries.

**Workflow.** `workflow.py` and its state/definition/execution/recovery modules implement sources → requirements → design → coverage/completion → materialize → execute → diagnose/maintain → knowledge. Host AI claims `next` work and submits proposals; deterministic stages and validation run in the kernel. Workflow, item, attempt and operation IDs are independent. Lease tokens fence stale submissions; idempotency keys are bound to request content. Long tasks use heartbeat/release. `revise` starts a source-backed new cycle without erasing old failures. A completed task can have a violated or incomplete business conclusion. Candidates stay staged while every required repetition executes; maintenance publishes only satisfied candidates through a locked content-hash comparison. Initial materialization also publishes only verified passing candidates with eligible dependencies; failed, blocked, cancelled and unverified candidates remain staged and in reports/evidence, never in the reusable case library. Partial publication exposes the exact published IDs and withheld reasons. Never change an oracle to match an observed bug merely to turn the run green.

**Recording.** `record stop` retains candidates, records observations and, outside workflow bindings, queues separate UI and cold HTTP validation through the existing runner. It does not publish candidates or auth before validation. `run-status` is read-only; only returned `published_ids` establish library publication. `recorder/session.py` drives the `agent-browser` binary (`recorder/agent.py`). The default session keeps its recording in `workspace/.local/recording.json`; `--session` or `AUTOSKILL_SESSION` selects an independent browser and recording under `.local/recordings/<hash>/`. Keep the same identity for every command in one AI task. Use the task's explicit workflow binding when recording managed work; the recorder captures that binding at start. Operation intents precede external mutations and receipts follow them; unknown effects require evidence-based recovery, not blind replay after lease expiry. Failed checks retain their declared expected value, actual observation and verdict. `record stop` compiles UI steps and business API traffic. HAR-derived checks are observations, not independent requirement oracles. Correlated response values become `{{variables}}` with a dependency on the matching resource's producer; ambiguous values stay literal with a compile note. `recorder/capture.py` preserves supplementary CDP traffic separately from original HAR, including available stream bytes and authentication. `conversation build` maps explicit captured fields into multi-turn assets; business expectations must be supplied independently.

**Case model.** Cases are JSON files validated by `core/store.py` against `references/case.schema.json`. UI steps are an engine-independent IR defined by the `ACTIONS` and `ASSERTIONS` tables in `replay/ir.py`. Adding an action or assertion means touching `ir.py`, `replay/ui.py`, both drivers if it needs a new primitive, the embedded shared support in `replay/codegen.py`, the recorder command in `recorder/session.py`, and `SKILL.md`. `case_editing.py` conditionally saves complete UI/API definitions; the server owns revision increments and preserves unknown metadata and prior evidence. Transport-only action identities fix the existing action count and order while operation types and assertions remain editable. A save never starts execution, and changed business prose cannot establish new oracle coverage by itself.

**Execution and evidence.** `runner.prepare` freezes cases, dependency closure, configuration, credentials, domain inputs and engine identity before `enqueue`; `execution_inputs.py` verifies and supplies that snapshot to execution. Candidate overrides do not write live cases. Results bind case content and execution scope hashes to actual attempt receipts and artifacts; hashes alone do not prove execution. `result_evidence` verifies frozen local evidence, while `result_current` additionally compares current inputs. Every retry keeps a separate attempt and screenshots. `replay/ui.py` is the common step loop; browser drivers supply primitives, and `replay/api.py` handles HTTP. Standalone UI scripts embed the same action loop, assertion poller and primitive drivers, including ordered locator fallback, XPath, and frame/open-shadow contexts. They still stop at the first failed assertion, require manual captcha input, omit managed saved-login/history/screenshots and cannot include API prerequisites in a pure UI export. Do not claim all exported/native engines have identical semantics.

**Verdicts.** Action completion is distinct from business verification. No assertion, an observation-only oracle or a reused-login probe cannot establish that the full business scenario passed. Retain an earlier business failure through retries, later successes and environmental blockers. Keep execution, business, declared performance targets and answer quality distinct: business Pass plus a failed SLA is still overall Fail. Temporal assertions are sampled; transition-from-false is appropriate only for an explicit state change, not every click or idempotent operation.

**State projection.** `task_state.py` derives the shared `state` object for lifecycle/phase, overall outcome, business/performance/quality checks, evidence, report and delivery. Raw stored verdicts remain historical facts. Current case validation compares the complete current input scope while historical runs retain their own results. Dashboard counts, filtering and detail share this projection; historical attempt metrics are labelled separately. Read-only status does not claim work, execute cases or render reports. The dispatcher reconciles deterministic workflow transitions every 200 ms; dashboard checks small revisions every 250 ms. The host proxy supports session-scoped revision reads; conversation tool cards remain request-driven and do not restore passive polling or a task dock. Foreground online acceptance requires state propagation within one second. Workflow report snapshots are frozen before starting a new cycle; export failure requires explicit retry, including an interrupted renderer after coordinator restart. The renderer never holds the project lock while writing Excel.

**Native assets and AI evaluation.** `native_assets.py` versions original file trees, entry arguments and working directories in the domain store; `native_run.py` freezes and executes them through the `engines` registry. Probe the actual runtime; unavailable tools produce Blocked, not success or an automatic download. Native reports and artifacts determine results, not exit code alone. `ai_eval` keeps a conversation's history, cookies and server bindings within one case, with separate contexts across cases. `dialogue_judge.py` persists frozen requests, host leases and independent review receipts. Natural-language replies may cite frozen context/user facts/reference values; record `facts_used` and hashes without pretending structural validation proves semantic correctness. Unknown facts remain unresolved. Only explicit `expected_phase="final_answer"` or checks with `when="final_answer"` defer their oracle during clarification; a judge cannot erase an immediate assertion failure. Keep asynchronous native execution so the active host can service judge requests instead of blocking on itself.

**Scheduling and host delivery.** Runs are atomically claimed from SQLite. `server/jobs.py` maintains one independent dispatcher, drains queued IR/native work and ticks enabled schedules after the CLI exits; it retires when no queued/running work or enabled schedules remain. `AUTOSKILL_MAX_PARALLEL` sets the process budget (default 2); shared saved-login access remains serialized, while isolated native runs may execute concurrently. `server/scheduler.py` owns schedule revisions and occurrence identities, committing the occurrence and enqueue/outbox together. `server/deliveries.py` and the DSH host adapter persist delivery intents and receipts. Unknown delivery is investigated before resend. Host acceptance is not workflow completion, and the adapter does not create a second recurring schedule in DSH. The host must be running to perform AI work; this is not machine wake-up or autonomous model inference in Python.

**Three kinds of placeholders.** `${ENV:NAME}` is a credential (`secrets.py`), `{{name}}` is a value extracted from an earlier API response, and `{{RAND}}` is text that is new on every run so created data never collides.

**Data.** The external data root contains all autoSkill user state. `projects/<id>/` contains: project/config/auth JSON, `testcases/*.json`, knowledge, generated `SKILL.md` and `domain/`. `domain.py` stores source documents, workflow definitions, requirements, scenarios, oracles and native assets as immutable generations and content-addressed objects, publishing one atomic `HEAD.json`. Durable staging uses `.local`; publication checks the expected generation or unchanged affected paths. SQLite is local runtime state, leases, receipts, schedules and indexes, not a second editable authority for definitions. `.local/` also holds credentials, saved sessions, settings, case sheets and run evidence. New internal path references are root-relative POSIX paths; `data_refs` resolves explicit legacy root aliases without changing historical bytes or hashes. Public CLI/HTTP paths follow the currently selected copy, even when the original tree still exists. Process ownership includes machine, data location and process birth; copied numeric PIDs cannot authorize signals or prove a local worker exists. Reentrant process/thread locks protect shared operations; acquire project locks before SQLite write transactions. Case publication uses `projects.save_cases(expected_hashes=...)` to preserve the exact tested candidate body. Filesystem publication plus SQLite receipts use recoverable journals, not a claimed cross-store transaction or external exactly-once guarantee. Complete data export or a stopped whole-folder copy includes credentials, saved logins, history and all evidence. Program replacement does not migrate or overwrite data. The old upgrade command and standalone helper are removed; initial legacy import is a separate built-in data operation. Project/runtime packs intentionally include credentials and saved logins when requested but omit local run history; ordinary project packs retain optional encrypted credential export. Imported definitions do not inherit another machine's verified local execution history.

**Case sheet.** The primary host task first delivers the complete 14-column design, executes its rows, updates that same public workbook and publishes only successful reusable UI/API candidates. Users do not create dashboard tasks or fill JSON. `plan.py` keeps default design sheets in `.local/case-plans/default/autoskill-cases`; named sessions use `.local/case-plans/<hash>/autoskill-cases`. Known external legacy sheets are copied into the data root and registered through explicit path mappings during initial adoption. `AUTOSKILL_CASE_SKILL` chooses the matching imported sheet when a mapping exists, and remains compatible with explicit external paths before initialization. `plan write` retains its eleven-column operational `excel` and returns a separate fourteen-column `delivery_excel` for users. Source fields absent from the operational sheet are bound to the business row hash in `functional-design.json`; do not infer them from HTTP paths or discard them before `record stop --plan`. A design row is not executable until actual actions/assertions are linked. Applying prose alone leaves its new functional expectation unverified; recorded source/check bindings or source-backed workflow oracles and actual regression must establish coverage. The initial public workbook is preserved separately. `plan.bind_execution` binds task ID, design row hash, frozen candidate and explicit run ID; `plan.sync(run_id=...)` updates failed unpublished candidates without consulting the live library or another task’s latest run. Each task keeps its own bindings, delivery path and report head: a late completion updates its original workbook after a new task replaces the active sheet, without changing the new internal sheet. Recording preserves the design task observed at start; a late candidate cannot be relabelled as a newer identical task. Whole-sheet snapshots retain unexecuted rows and original expectations; export retries do not run or publish cases. Design sheets register automatically by project and session for read-only dashboard discovery. Execution completion synchronizes the sheet through the common service, and current verdicts require matching content/input evidence. A manually marked cell is not execution proof. The folder remains replaceable by another of the same name.

**Task delivery.** Every completed recording, run and workflow cycle produces its own Excel, concise Markdown and Bug Markdown from the same frozen task snapshot. `task_reports.py` persists generation receipts, file hashes and retry failures; retrying export must not execute tests or borrow another task's latest results. The bundled `references/test-cases` skill specifies the 14-column workbook and real business grouping. Display FT identifiers map back to immutable case identities and versions; all attempts and earlier failures remain available. The brief contains only basic fields, result counts, major issues and an Excel link. The issue list distinguishes business failures, execution problems, unverified failures, recording observations and historical failures; later success cannot erase an earlier failure. `ready` requires all three files to exist and pass readback checks. Completing an older delivery preserves its original workbook, Markdown and frozen snapshot bytes. The dashboard also exports a self-contained HTML using the same report components, with all details and embedded available screenshots for offline reading. These artifacts do not replace execution evidence or prove a DSH native file-card delivery.

**Dashboard.** `server/app.py` is a FastAPI app bound to loopback; `server/metrics.py` selects indexed scope in SQL and derives verified figures from shared state projections within one read snapshot, so cards and lists agree. Current case badges qualify actual evidence and the complete current input scope, including dependency changes; raw stored results remain historical facts. Reindexing unchanged project files does not rewrite business rows or trigger another refresh. The UI uses hash routing and the `h()` helper in `ui/js/core.js`. `server/ui_assets.py` serves fresh HTML and places CSS/JS under a whole-UI content revision; keep module imports relative so transitive and dynamic imports use that revision too. Static responses do not reuse timestamp/size validators or clear user storage. Each DSH client activation uses a new iframe URL, stable across ordinary React renders. An upgrade must reload the host's plugin module; code already running in an old iframe cannot update itself.

**Validation boundaries.** See [the architecture review](docs/架构审查与演进方案.md), [the system/dialogue report](reports/系统化技能与多轮对话验证.md) and [this round's DSH acceptance](reports/DSH真实验收.md). Linux browser/HTTP/native fixtures exercise real transports; they are not production capacity or model-accuracy measurements. Earlier DSH acceptance used a local protocol model and its remote connection was blocked by CONNECT 403. The current round connects the actual DSH host to the requested remote model and verifies parameterless skill activation, bound sandbox commands and real UI execution; consult the current report for each target, failure and remaining gap. Keep native tests against frozen dashboard sources separate from inspection of the actual outer DSH iframe. WebRTC audio acceptance remains Blocked by managed browser ICE policy; WebSocket audio is a separate tested transport. Windows and UOS have not received device acceptance in this round. Keep first-attempt stability, retry-assisted success, quality pass rate and unfinished/blocked counts separate; a fixture success fraction is not AI accuracy.

## Product rules set by the maintainer

- No guard rails on the user's own cases: no access-scope settings, no risk approvals, no feature limits. Do not reintroduce them. The legacy `scripts/qa.py` path in `core/store.py` still has an approvals check; `autoskill run` and the dashboard do not use it.
- Credentials and saved logins are plain text on the local machine and shown in project settings. Sharing them in `pack --full` is intentional; describe what the pack includes accurately, without adding approvals or a passphrase requirement. `seal`/`unseal` in `secrets.py` exist only to read stores written by older versions.
- Browser recording, replay, login and host tasks use the selected data root's saved `dashboard.headed` choice through `paths.headed()`. Explicit `--headed` / `--headless` or `AUTOSKILL_HEADED=1/0` overrides that default. Without a saved choice, windows are visible and maximised; Linux without a display defaults to headless. Scheduled replay tasks retain their explicit per-task choice; legacy tasks without one follow the saved dashboard preference. Host prompts must propagate an explicit user request to show or hide the browser; only an unspecified choice follows saved preferences. Manual login keeps the recording and its browser/task identity alive, and continuation reads the same session with a fresh snapshot.
- One site (host and port) is one project; creating a project for a known site returns the existing one. A case's `module` is its sub-project. Project visibility follows the entry's purpose: test-sheet and workflow views include projects with designs or tasks before reusable cases exist; the reusable-case view lists projects with saved cases.
- Generated assertions should be few and stable: assert the direct result of the action, never volatile data such as totals, order, timestamps or ids.
- Pages, scripts and styles get no API case; only business requests do.
- Playwright replay and recording use the user's installed Chrome by default and fall back to the bundled browser when it is missing or will not start (`paths.chrome()`, `autoskill settings --browser`, `AUTOSKILL_BROWSER`). Selenium always uses the bundled browser because the driver must match its version.
- The dashboard follows Apple platform conventions: one accent colour, neutral grouped backgrounds, translucent materials for menus and the toolbar, floating inspector panels, spring-like motion. Replay preferences live in one place, the toolbar's 回放设置 popover; do not scatter per-button options.

## Releases

`.github/workflows/release.yml` builds the Windows x64 and two native Linux packages on a tag and publishes them as release assets; runtime binaries never enter git history. Publication requires the Linux x64 browser evidence and interruption tests against the newly built runtime; skipped browser checks fail that gate. This does not establish Windows or UOS device acceptance. `scripts/record-release-*.py` commit status documents to `main` during a release, so `main` can move underneath local work: fetch before pushing. The version lives in both `package.json` and `app/autoskill/__init__.py`.

`.gitattributes` forces LF everywhere except `*.cmd` and `*.bat`.
