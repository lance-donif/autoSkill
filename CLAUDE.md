# CLAUDE.md

Development and delivery guidance for agents working in this repository.

## What this is

autoSkill is a local test system operated through an agent skill, CLI and dashboard. The host AI designs cases from source material and can use `workflow` for resumable requirements and maintenance work. The kernel validates references, executes frozen inputs, retains evidence and publishes eligible cases. It supports browser recording, Playwright/Selenium/HTTP replay, Locust API load testing, native Python and Postman/Apifox assets, and multi-turn HTTP/SSE/WebSocket evaluation with host judgements. It ships as an offline package and as a DeepSeek Harness (DSH) plugin. The host supplies the model configuration.

User-facing text (CLI messages, dashboard, SKILL.md, docs) is Chinese; code comments and docstrings are English.

## 仓库交付分工

除非用户明确指定其他协作方式，涉及代码、测试、CI 或 PR 的交付由主智能体监管。主智能体只负责拆分任务、确定验收标准、协调子智能体、核对证据和最终把关。执行子智能体负责编写代码、编写并运行测试、配置并运行 CI、提交变更和处理 PR。宣布完成前，由一位未参与本次实现的独立子智能体实际复验，主智能体核对复验证据后确认交付。

## Layout

- `skills/autoskill/` is the product. `SKILL.md` is the contract the agent reads, `app/autoskill/` the Python package, `app/ui/` the dashboard (plain ES modules, no build step), `models/captcha/` the bundled captcha model. `vendor/` (bundled runtime) is git-ignored. User data defaults to the external `~/autoSkill-data` directory (Windows `%USERPROFILE%/autoSkill-data`); explicit `AUTOSKILL_WORKSPACE` selects another root.
- `plugin/` integrates with the DSH host. `index.mjs` starts the dashboard and registers the skill against the confirmed data root. `host-adapter.mjs` delivers durable work to host sessions. Native tools, pre-step summaries and authenticated routes use the same kernel. The argument-free `/autoskill-use` command loads the registered skill into the current session for the next user turn. `client.js` supplies collapsed inline tool results and sidebar dashboard panels at the origin provided by host metadata. Keep the conversation free of an input dock, automatic task popups and forced todo entries.
- In the offline package the skill sits at `autoskill/`, in a checkout at `skills/autoskill/`; `findSkillDir` in the plugin and `paths.SKILL` handle both.
- `scripts/` holds maintainer review, build and release tools. `preview/` is the standalone GitHub Pages demo. The offline packages ship the product dashboard. `reports/` holds dated validation evidence. Keep raw authentication and network captures out of public reports.

## Architecture

**CLI and services.** Machine-facing commands in `cli.py` emit one JSON object. Successful queries and queue submissions return 0. A synchronous run, assertion, `doctor` or `verify` check that reports failure returns 1. Command errors and blocked synchronous runs return 2. The dashboard command starts the long-running loopback service. CLI and HTTP share application services. In a restricted or host-bound process `bridge.py` can forward structured arguments and selected attachments to `/api/bridge`. Resolve paths at the caller and preserve attachment content identity across transport. Carry the workspace, host session, browser session and workflow binding separately. Read complete definitions through the service APIs and respect pagination cursors and snapshots.

**Workflow.** `workflow.py` and its state/definition/execution/recovery modules implement sources → requirements → design → coverage/completion → materialize → execute → diagnose/maintain → knowledge. Host AI claims `next` work and submits proposals; deterministic stages and validation run in the kernel. Workflow, item, attempt and operation IDs are independent. Lease tokens fence stale submissions; idempotency keys are bound to request content. Long tasks use heartbeat/release. `revise` starts a source-backed new cycle without erasing old failures. A completed task can have a violated or incomplete business conclusion. Candidates stay staged while every required repetition executes; maintenance publishes only satisfied candidates through a locked content-hash comparison. Initial materialization also publishes only verified passing candidates with eligible dependencies; failed, blocked, cancelled and unverified candidates remain staged and in reports/evidence, never in the reusable case library. Partial publication exposes the exact published IDs and withheld reasons. Never change an oracle to match an observed bug merely to turn the run green.

**Recording.** `record stop` retains candidates, records observations and, outside workflow bindings, queues separate UI and cold HTTP validation through the existing runner. It does not publish candidates or auth before validation. `run-status` is read-only; only returned `published_ids` establish library publication. `recorder/session.py` drives the `agent-browser` binary (`recorder/agent.py`). The default session keeps its recording in `.local/recording.json` under the selected data root. `--session` or `AUTOSKILL_SESSION` selects an independent browser and recording under `.local/recordings/<hash>/`. Keep the same identity for every command in one AI task. `record start --reuse` executes the selected saved UI case as a version-bound prerequisite in the recording tab before new steps are captured. Use the task's explicit workflow binding when recording managed work; the recorder captures that binding at start. Operation intents precede external mutations and receipts follow them; unknown effects require evidence-based recovery, not blind replay after lease expiry. Failed checks retain their declared expected value, actual observation and verdict. `record stop` compiles UI steps and business API traffic. HAR-derived checks are observations, not independent requirement oracles. Correlated response values become `{{variables}}` with a dependency on the matching resource's producer; ambiguous values stay literal with a compile note. `recorder/capture.py` preserves supplementary CDP traffic separately from original HAR, including available stream bytes and authentication. `conversation build` maps explicit captured fields into multi-turn assets; business expectations must be supplied independently.

**Case model.** Cases are JSON files validated by `core/store.py` against `references/case.schema.json`. UI steps are an engine-independent IR defined by the `ACTIONS` and `ASSERTIONS` tables in `replay/ir.py`. Adding an action or assertion means touching `ir.py`, `replay/ui.py`, both drivers if it needs a new primitive, the embedded shared support in `replay/codegen.py`, the recorder command in `recorder/session.py`, and `SKILL.md`. `case_editing.py` conditionally saves complete UI/API definitions; the server owns revision increments and preserves unknown metadata and prior evidence. Transport-only action identities fix the existing action count and order while operation types and assertions remain editable. A save never starts execution, and changed business prose cannot establish new oracle coverage by itself.

**Execution and evidence.** `runner.prepare` freezes cases, dependency closure, configuration, credentials, domain inputs and engine identity before `enqueue`; `execution_inputs.py` verifies and supplies that snapshot to execution. Candidate overrides do not write live cases. Results bind case content and execution scope hashes to actual attempt receipts and artifacts; hashes alone do not prove execution. `result_evidence` verifies frozen local evidence, while `result_current` additionally compares current inputs. Keep a separate receipt for each executed attempt and bind any captured screenshots to that attempt. `replay/ui.py` is the common step loop; browser drivers supply primitives, and `replay/api.py` handles HTTP. Standalone UI scripts embed the shared actions, assertion polling and driver primitives, including ordered locator fallback, XPath, and frame/open-shadow contexts. They stop at the first failed assertion and prompt for captcha input. API prerequisites, managed saved logins, run history and screenshots belong to the managed executor.

**Case outcomes.** `task_state.case_outcome` projects each target to `pass`, `fail` or `not_run`. A started target passes when its configured steps and checks complete and execution evidence is valid. With no business assertion, replay uses the completed step or HTTP record. Cancellation or blockage before target start is `not_run`. Interruption after target start, a failed check or missing evidence for a claimed pass yields `fail`. A complete replay can keep an execution pass for observation-only or unmapped checks while the business result stays unverified. Reusing a login probe does not verify the full target. Preserve earlier business failures through retries, and keep business, performance and answer-quality results distinct. A failed declared SLA makes the overall outcome fail. Use a transition-from-false assertion only for an explicit state change.

**State projection.** `task_state.py` is the shared source of lifecycle and phase, outcome, business/performance/quality checks, evidence, report and delivery. Historical runs retain their recorded facts. Current case validation compares the current input scope, including dependencies. Dashboard counts, filtering and details use the same projection. Label historical attempt metrics separately. Status reads have no execution or export side effects. The dispatcher checks for deterministic transitions on its 200 ms loop and the foreground dashboard polls revisions every 250 ms. The host proxy supports session-scoped revision reads. Conversation tool cards are request-driven. Foreground online acceptance requires state propagation within one second. Freeze workflow reports before a new cycle and render them outside the project lock. Failed or interrupted exports require explicit retry.

**Native assets and AI evaluation.** `native_assets.py` versions original file trees, entry arguments and working directories in the domain store; `native_run.py` freezes and executes them through the `engines` registry. Probe the actual runtime; unavailable tools produce Blocked, not success or an automatic download. Native reports and artifacts determine results, not exit code alone. `ai_eval` keeps a conversation's history, cookies and server bindings within one case, with separate contexts across cases. `dialogue_judge.py` persists frozen requests, host leases and independent review receipts. Natural-language replies may cite frozen context/user facts/reference values; record `facts_used` and hashes without pretending structural validation proves semantic correctness. Unknown facts remain unresolved. Only explicit `expected_phase="final_answer"` or checks with `when="final_answer"` defer their oracle during clarification; a judge cannot erase an immediate assertion failure. Keep asynchronous native execution so the active host can service judge requests instead of blocking on itself.

**Scheduling and host delivery.** `server/jobs.py` drives the SQLite queue after the CLI exits. It ticks schedules, starts replay, native and load runs, reconciles workflows and processes pending report work. It retires after an idle period. `AUTOSKILL_MAX_PARALLEL` sets the process budget (default 2). Shared saved-login access is serialized and isolated native runs may execute concurrently. `server/scheduler.py` commits each occurrence together with its run or delivery intent. `server/deliveries.py` and `plugin/host-adapter.mjs` persist intents and receipts. Investigate unknown delivery before resend. The local scheduler owns recurrence. Host acceptance records delivery, and any AI work requires a running host.

**Placeholders.** `${ENV:NAME}` resolves a credential from the local store or process environment. `{{name}}` can reference an API input or a value extracted from an earlier response. `{{RAND}}` uses a generated value frozen for the run.

**Data.** The selected data root holds `projects/<id>/` (project, config, auth, cases, knowledge, generated skill and `domain/`) and `.local/` (SQLite, credentials, saved sessions, settings, design sheets and run evidence). `domain.py` publishes source documents, workflow definitions, requirements, scenarios, oracles and native assets as immutable generations behind an atomic `HEAD.json`. Stage changes in `.local` and check the expected generation or affected paths before publication. SQLite holds runtime state, leases, receipts, schedules and indexes. Store new internal paths relative to the data root in POSIX form. `data_refs` resolves legacy aliases to the selected copy while preserving evidence bytes and hashes. Process ownership includes the machine, workspace and process birth. Acquire project locks before SQLite write transactions. Publish tested case bodies with `projects.save_cases(expected_hashes=...)`. Recoverable journals coordinate filesystem publication with SQLite receipts.

Updating the program reuses the selected data root. `data import` copies an existing data directory or archive into an empty target. `data export` or a stopped whole-folder copy carries credentials, saved logins, history and execution evidence. Project and runtime sharing packs omit `.local` run history. Imported definitions need local execution evidence to qualify as currently verified. [Data retention and import](docs/升级与数据保留.md)

**Case sheet.** The host first delivers the complete 14-column design. It executes the rows, updates the same public workbook and publishes only reusable UI/API candidates with the required passing execution evidence. Users can start this flow in conversation. `plan write` returns the 11-column operational `excel`, the public `delivery_excel` and the preserved `initial_excel`. `paths.case_skill()` selects `.local/case-plans/default/autoskill-cases` or the named session's sheet. `AUTOSKILL_CASE_SKILL` can select an explicit folder or its mapped imported copy. Bind source fields in `functional-design.json` to the business row hash. Keep business wording and grouping from the source. Link each design to executable actions and checks, then verify its expectation in an actual run. A manually marked row still needs run evidence to qualify as verified.

`plan.bind_execution` records the design task, row hash, frozen candidate and explicit run ID. `plan.sync(run_id=...)` updates the original delivery even if the candidate stays unpublished or a newer design has replaced the active sheet. Keep unexecuted rows, their original expectations, task-specific bindings and the frozen initial workbook. The dashboard discovers sheets by project and session and conditionally saves design rows. [Case design and execution](skills/autoskill/SKILL.md)

**Task delivery.** Recording, execution and workflow reports each use their own frozen task snapshot. `task_reports.py` stores receipts, file hashes and export failures. The `ready` receipt requires successful readback of the Excel, concise Markdown and Bug Markdown. The workbook opens on 概览, with charts when the snapshot contains cases. The 14-column case sheet groups rows by business area. Display FT identifiers map back to the immutable case IDs and versions. The brief contains basic fields, result counts, major issues and an Excel link. The issue list distinguishes business failures, execution problems, unverified failures, recording observations and historical failures. Preserve every attempt and earlier failure. Retry export against the original task snapshot and preserve the bytes of previously completed deliveries. The dashboard's standalone HTML uses the live report components and embeds available screenshots for offline reading. A claim about a native DSH file card requires evidence from the host.

**Dashboard.** `server/app.py` serves the loopback FastAPI dashboard. `server/metrics.py` computes the overview, recent runs and failure list within one read snapshot. The overview's pass rate uses the latest batch in scope, and load runs have separate statistics. Reindexing unchanged definitions preserves the existing revision. The UI uses hash routing and `h()` from `ui/js/core.js`. `server/ui_assets.py` serves fresh HTML and versions the entire CSS/JS graph by content. Use relative imports, including dynamic imports. Preserve user storage across upgrades. Each DSH client activation uses a fresh iframe URL that stays stable across ordinary React renders. Reload the host's plugin module when replacing the program.

**Validation evidence.** Attribute a result to the tested revision, runtime, platform and actual target. Report fixture coverage, live DSH host and iframe checks, remote-model runs and device acceptance at their observed scope. Track first-attempt stability, retry-assisted success, measured answer quality and unfinished or blocked work separately. Record the measured transport for voice tests. Release and DSH reports retain dated evidence and known gaps. [Release verification](reports/交付验证报告.md) · [DSH acceptance](reports/DSH真实验收.md) · [Platform support](docs/平台与第三方支持.md)

## Product rules set by the maintainer

- Users run their own cases as written, without access-scope settings, risk approvals or feature limits. The compatibility executor called by `skills/autoskill/scripts/qa.py` has a separate approvals check. The supported replay CLI and dashboard use `runner.py`.
- Store credentials and saved logins in plain text locally. Project settings display credential values and saved-login status. `pack --full` includes saved credentials and login state without a passphrase. Ordinary `pack` supports optional passphrase-encrypted export of referenced credentials. Keep support for reading older encrypted stores.
- Browser recording, replay, login and host tasks use the selected data root's saved `dashboard.headed` choice through `paths.headed()`. Explicit `--headed` / `--headless` or `AUTOSKILL_HEADED=1/0` overrides that choice. The default is a visible, maximised window. A Linux launch without a desktop reports the display requirement. Scheduled replay tasks retain their explicit per-task choice; legacy tasks without one follow the saved dashboard preference. Host prompts must propagate an explicit user request to show or hide the browser and follow the saved choice otherwise. Manual login keeps the recording and its browser/task identity alive, and continuation reads the same session with a fresh snapshot.
- One site (host and port) is one project; creating a project for a known site returns the existing one. A case's `module` is its sub-project. Project visibility follows the entry's purpose: test-sheet and workflow views include projects with designs or tasks before reusable cases exist; the reusable-case view lists projects with saved cases.
- Generated assertions should be few and stable: assert the direct result of the action, never volatile data such as totals, order, timestamps or ids.
- Pages, scripts and styles get no API case; only business requests do.
- Playwright replay and recording prefer the user's installed Chrome by default, with a bundled fallback when it is missing or fails to launch. `autoskill settings --browser` and `AUTOSKILL_BROWSER` select that preference. Selenium uses the browser and matching ChromeDriver from the configured runtime pair, which defaults to the bundled pair in the offline package. Linux setup also supports an explicitly selected system pair.
- The dashboard follows Apple platform conventions: one accent colour, neutral grouped backgrounds, translucent materials for menus and the toolbar, floating inspector panels, spring-like motion. Replay preferences live in one place, the toolbar's 回放设置 popover; do not scatter per-button options.

### Dashboard details and browser regressions

- Match the case inspector and execution report layout in `bac57dc`. Use the light and dark palette from `e0b26b0` across the five dashboard menus and standalone HTML. Keep colour values in the shared palette.
- A UI case opens on its ordered replay steps and checks, with available script downloads. An API case opens on the request, followed by its assertion rules. Show prerequisites when present. The case footer contains Close and, for replayable cases, Run. Editing, moving, deleting and load testing are list actions. Closing the inspector preserves the user's folder, filters and scroll position.
- Show UI execution assertions, the ordered step evidence and available screenshots. Match historical evidence by run, case and revision. Distinguish definition-only steps and steps never reached from executed steps. In API results show the HTTP summary before assertions and pair each request with its own response on retries. The live report and the downloaded HTML use the same evidence. Pages simulations freeze mock inputs at launch and remain entirely in the preview.
- Update the corresponding Chromium regressions in the same change as an intentional change to these behaviours. The `dashboard-e2e` job lists the exact Playwright/Chromium invocation for desktop and phone layouts, report content, offline downloads and palette checks. [Dashboard E2E](.github/workflows/lint.yml)

### Load testing and reporting

- Keep the 压测记录 entry under 执行记录 and keep the existing single-case and batch launch actions. Use two tabs named 性能测试 and 压力测试. The performance form has exactly three numeric fields, 并发数, 持续时间（秒） and 目标请求数. Concurrency is required and either or both limits may be set. Start the clock at the automatic rendezvous release. Stop admitting target samples at the first configured limit, then retain the completed in-flight samples. Limits apply to each independently queued project run.
- Run new load tests through Locust in an isolated worker process. Offer only saved API cases, and keep regular page replay in the case library. Count each admitted target HTTP execution once. Prerequisite setup does not consume the target budget. A pressure run adds workers in stages, holds the maximum stage for its full duration and assigns each sample to the stage in which it starts. Freeze the selected mode, settings and case versions at enqueue. Read legacy configurations and results as performance runs.
- Use Apache JMeter 5.6.3 dashboard labels and calculations for APDEX, request summary, statistics, errors and sampler errors. Keep the performance report focused on response time and the pressure report focused on changes in load and its stage breakdown. Use measured sample and thread data and leave missing fields blank or display an em dash. Reuse the same data and layout in standalone HTML and exercise both report modes in Chromium on PRs. Pages runs use local simulation only.

## Releases

A `v*` tag push or a manual dispatch on `main` with an existing release tag builds Windows x64, Linux x64 and Linux ARM64 from the tagged commit. Use the native jobs for the pinned asset fetch, bundle and ZIP commands. Both Linux jobs check the packaged browser configuration. Linux x64 also runs the required browser, recorder, knowledge, native-evidence and load tests with the bundled runtime and rejects skips. Publication requires all three archives and the Linux x64 validation log. Runtime binaries stay out of git. Release jobs commit progress and results to `main`, so fetch before pushing. Keep `package.json` and `skills/autoskill/app/autoskill/__init__.py` at the same version. [Release workflow](.github/workflows/release.yml)

`.gitattributes` uses LF for text and CRLF for `*.cmd` and `*.bat`, and preserves binary assets.
